# Optional TLSNotary presentation verifier

This standalone Rust binary performs **offline cryptographic verification** of
TLSNotary `v0.1.0-alpha.15` presentations. It pins upstream commit
`47aee45b53e06648c1b2ad3689b367b8c923fdec` and links `tlsn-attestation` and
`tlsn-core`, without the MPC/prover stack or a network client. Its dependency
resolution is recorded in `Cargo.lock`.

TLSNotary describes this release as experimental and unsuitable for production.
This adapter preserves that status. It verifies a trusted notary's attestation,
the TLS server identity and requested authenticated transcript bytes; it is not
a SNARK verifier or proof of exactly-once HTTP execution. It does not generate
presentations or attach a proof to an earlier ordinary `zkweb fetch` result.
[Pinned upstream README](https://github.com/tlsnotary/tlsn/blob/47aee45b53e06648c1b2ad3689b367b8c923fdec/README.md),
[upstream verification example](https://github.com/tlsnotary/tlsn/blob/47aee45b53e06648c1b2ad3689b367b8c923fdec/crates/examples/attestation/verify.rs).

## Build and test

Use Rust 1.95 or newer; this project is tested with the repository's Rust 1.99
toolchain. The first build downloads the pinned dependencies. Verification and
tests themselves run without contacting a notary or origin.

```sh
cd research-mixnet/proof-verifier
cargo build --locked --release
cargo test --locked
```

The root CLI expects `zkweb-tlsn-verify` beside the `zkweb` executable. Its
optional build target handles that placement. This crate has its own workspace,
so building it does not build or alter the legacy wallet/protocol workspaces.

## Input protocol

Read exactly one JSON object from stdin:

```json
{
  "format": "zkweb-tlsn-verify-v1",
  "presentation_base64": "BASE64_OF_PRESENTATION_JSON_BYTES",
  "policy": {
    "server_name": "example.com",
    "notary_key_hex": "COMPRESSED_SECP256K1_PUBLIC_KEY_HEX",
    "min_time": 1700000000,
    "max_time": 1700000300,
    "sent_ranges": [],
    "received_ranges": [{"start": 0, "end": 8}]
  }
}
```

The presentation is **upstream `Presentation` serialized as JSON**, wrapped in
standard base64. Bincode artifacts are not accepted. Duplicate JSON fields,
unknown request/policy fields, trailing input, malformed base64 and unsupported
notary algorithms fail closed.

The caller supplies a trusted notary key independently of the artifact. This
version accepts only a canonical lowercase 66-character compressed K256 public
key, including its `02` or `03` prefix. The expected server name is lowercase.
Both UNIX timestamp bounds are required, positive and inclusive, with
`min_time <= max_time`. The notary's signed connection time is checked against
that caller-selected window; old fixtures require an explicit historical
window. A time window is not a verifier challenge or replay-prevention store.

Ranges are end-exclusive byte offsets in the **raw application transcript**,
including HTTP start lines and headers. Each direction permits at most 64
sorted, non-overlapping, nonempty ranges. The complete selected range must be
authenticated by the proof. No bytes are disclosed by default. The binary does
not parse HTTP, infer a response body, verify a JSON predicate, or replace
redacted bytes with believable text.

## Output and limits

Success writes one `zkweb-tlsn-verified-v1` JSON object containing
`backend_commit`, `server_name`, `notary_key_hex`, `time`, `sent_length`,
`received_length`, and the selected `sent`/`received` ranges with
`start`, `end` and `data_base64`. Only the selected authenticated bytes are
returned. A failure writes no successful output, prints a fixed diagnostic and
exits nonzero; upstream errors or panic diagnostics are not exposed.

- Input JSON: at most 24 MiB; decoded presentation JSON: at most 16 MiB.
- Full sent and received transcripts: at most 1 MiB each.
- Combined selected output data: at most 1 MiB.
- Hash openings: at most 256; structural containers and recursion are bounded.

The verifier checks sparse transcript totals and the signed transcript lengths
before typed upstream deserialization. This is necessary because upstream's
`PartialTranscript` deserializer expands compressed transcript totals into
vectors, so a small serialized file alone does not bound allocations.
[Pinned upstream transcript implementation](https://github.com/tlsnotary/tlsn/blob/47aee45b53e06648c1b2ad3689b367b8c923fdec/crates/core/src/transcript.rs).

Filtering output ranges does not erase information already disclosed inside a
presentation. A presenter must create the appropriate selective presentation
before sharing the artifact. The verifier's disclosure policy controls its
output, not how the artifact was produced.

## Fixtures and provenance

The vendored binary fixture comes from the pinned upstream repository. Its JSON
form is generated by `examples/convert_upstream_fixture.rs`, which accepts only
that compile-time, trusted fixture and has no arbitrary-file import interface.
The JSON and binary hashes, source URL and synthetic values are recorded in
[the fixture manifest](tests/fixtures/provenance.json).

The fixture's notary key is public test material generated from `[42; 32]`.
Its TLS identity is `tlsnotary.org` at time `1671637529`, but its HTTP plaintext
is synthetic (`Host: localhost` and a dummy response containing a test cookie).
It is a verification test vector, not evidence of a real website response.
Never configure a production verifier to trust this test key.

Tests check the actual upstream signature, certificate chain and transcript
commitments, plus wrong keys/domains/times, tampering, unsupported algorithms,
missing identity/transcript proofs, sparse-length expansion, disclosure bounds
and valid-but-redacted byte ranges. Partial-proof tests adapt the upstream
fixture generator under its MIT/Apache-2.0 licensing; see [UPSTREAM-NOTICE](UPSTREAM-NOTICE).
